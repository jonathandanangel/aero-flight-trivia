# Cursor migration guide

This document describes the current AeroGrid codebase and a safe sequence for
removing its Lovable dependencies. It is a plan, not a record of a completed
migration. Keep the Lovable project available until the replacement build has
been deployed and the new deployment has passed the acceptance checks below.

**Working-tree update (2026-09-11):** the 31 media files have been copied into
`src/assets/` and the four game components now import those local files. The
`.asset.json` stubs are gone. The remaining steps (replace the Vite wrapper,
remove Lovable telemetry/docs, disconnect GitHub sync) are still open.

## Executive summary

The game code is mostly portable. It has no database, authentication service,
Supabase project, API integration, or required environment variables. Campaign
progress is saved in the browser's `localStorage`, and audio is generated with
the browser Web Audio API.

There are two hard Lovable dependencies:

1. `@lovable.dev/vite-tanstack-config` currently assembles the Vite, React,
   Tailwind, TanStack Start, and Nitro build configuration.
2. All 31 image/video assets are Lovable asset manifests rather than media files.
   Their URLs use the Lovable-only `/__l5e/assets-v1/...` route.

The second item is the highest migration risk. The 31 source files total
27,399,079 bytes (about 26.1 MiB), including a 6.7 MB MP4. They are public on the
current `aero-flight-trivia.lovable.app` deployment, but a detached local Node
build returns 404 for the `/__l5e/assets-v1/...` paths. Copy these files before
disconnecting, unpublishing, or deleting anything in Lovable.

The repository's `origin` is already the normal GitHub repository
`https://github.com/jonathandanangel/aero-flight-trivia`; it does not need to be
replaced. What must be stopped later is Lovable's two-way synchronization with
that repository.

## Codebase overview

### Technology

- React 19 and TypeScript.
- TanStack Start for server-side rendering and file-based routing.
- TanStack Router and React Query. React Query currently only provides router
  context; no queries or mutations are implemented.
- Vite 8 for development and builds.
- Nitro 3 for the production server/deployment bundle.
- Tailwind CSS 4 with a large custom neon theme in `src/styles.css`.
- Radix/shadcn-style primitives under `src/components/ui`.
- Browser Web Audio; there are no checked-in audio files.
- No test runner is configured.

The runtime requires Node `>=22.12.0`. Node 24 LTS is the recommended team
default. The audited machine used Node 26.8.2 successfully.

### Application structure

- `src/routes/__root.tsx` defines the HTML shell, global metadata, not-found
  page, and React error boundary.
- `src/routes/index.tsx` is the only application route (`/`). It installs the
  game provider and renders `AeroGrid`.
- `src/router.tsx` creates the TanStack Router and Query Client.
- `src/start.ts` installs the server error and CSRF middleware.
- `src/server.ts` wraps the TanStack server entry so catastrophic SSR errors
  produce a usable HTML error page. Keep this file during the migration.
- `src/components/game/AeroGrid.tsx` is the main game state machine and screen
  coordinator.
- `src/components/game` contains the trivia interactions, diagrams, title and
  settings screens, celebrations, Electric Recall, Light Cycle, Neon Maze,
  Memory Gauntlet, briefing, and finale.
- `src/game/store.tsx` persists settings and campaign progress under
  `aerogrid99.save.v1` in `localStorage`.
- `src/game/audio.ts` synthesizes music and effects with Web Audio.
- `src/data/questions/a-foundations.ts` through `k-high-speed.ts` contain the
  333-question main curriculum.
- `src/data/questions/extreme-expansion.ts` supplies additional questions for
  the Extreme mode.
- `src/game/validate.ts` implements the in-app question-bank validator.
- `src/routeTree.gen.ts` is generated by TanStack Router and should not be
  edited manually.
- `public/robots.txt` and `public/sitemap.xml` currently point at the Lovable
  production hostname.
- `tmpscripts/f.ts` is an ad hoc question inspection script and is included by
  the current lint command.

### Data flow and external services

- There is no backend data store. Reload persistence is browser-local only.
- There are no application secrets or required `.env` variables in the current
  code.
- No application fetches, WebSockets, analytics SDKs, payment services, or
  third-party APIs were found.
- Google Fonts is loaded at runtime from `fonts.googleapis.com` and
  `fonts.gstatic.com`. This is external but is not a Lovable dependency. It can
  remain, or the fonts can be self-hosted later for offline/privacy needs.
- The live Lovable host and the 31 media paths are the only required network
  resources found for the game itself.

### Current verification baseline

The following was observed before migration:

- `npx tsc --noEmit`: passes.
- `npm run build`: passes and currently selects Nitro's
  `cloudflare-module` preset through the Lovable config wrapper.
- A framework-native replacement Vite config using Nitro's `node_server` preset
  was tested: it built successfully and served `/` with HTTP 200.
- That detached server returned HTTP 404 for a representative
  `/__l5e/assets-v1/...` request, confirming that the media must be vendored.
- The existing `npm run preview` command returned HTTP 500 after the current
  build because it looked for `dist/server/server.js` while the Nitro output was
  in `.output`.
- `npm run lint` is not currently green: 1,484 Prettier errors and 12 React
  warnings were reported. These are pre-existing and should be handled in a
  separate formatting/fix commit so they do not obscure the migration diff.

The repository currently mixes package-manager signals: `README.md` tells users
to use npm, while `bun.lock` and `bunfig.toml` configure Bun. Because there is no
committed `package-lock.json`, an npm install can resolve versions differently;
for example, `@lovable.dev/vite-tanstack-config` is declared as `^2.20.0`,
`bun.lock` records 2.20.0, and npm resolved 2.21.0 during this audit.

## Lovable dependency inventory

### Hard build-time dependency

- `package.json` lists `@lovable.dev/vite-tanstack-config`.
- `vite.config.ts` imports its `defineConfig` helper.
- The helper currently supplies Tailwind, React, TanStack Start, Nitro,
  tsconfig-path support, aliases, environment injection, React deduplication,
  Lovable diagnostics, sandbox settings, and a Lovable asset proxy.
- `bun.lock` records the Lovable package.
- `bunfig.toml` grants Lovable packages exceptions from its release-age rule.

The underlying framework packages are already direct dependencies or
devDependencies, so the wrapper can be replaced without changing the
application architecture.

### Hard runtime asset dependency

Every file under `src/assets` is currently a `*.asset.json` manifest containing:

- a Lovable `project_id` and `asset_id`;
- an R2 storage key;
- a relative `/__l5e/assets-v1/...` URL;
- the original filename, media type, and expected byte count.

All 31 manifests are used by:

- `src/components/game/ExtremeBriefing.tsx`;
- `src/components/game/WorldBackground.tsx`;
- `src/components/game/BrainCelebration.tsx`;
- `src/components/game/BrainOverload.tsx`.

The Lovable Vite package only proxies those routes when
`LOVABLE_PREVIEW_HOST` is set. It is not durable local or self-hosted storage.

### Lovable-only telemetry

- `src/lib/lovable-error-reporting.ts` calls globals injected by Lovable's
  editor/preview.
- `src/routes/__root.tsx` calls that helper from the React error boundary.

The calls are optional at runtime, but they should be removed or replaced so
the source no longer depends on Lovable globals.

### Sync, metadata, and branding

- `AGENTS.md` says the branch is synchronized with Lovable.
- `.lovable/project.json`, `.lovable/north-star.md`, and `.lovable/plan/**`
  contain Lovable project metadata and planning documents.
- `README.md` links to the Lovable editor and live Lovable app.
- `src/routes/__root.tsx` declares `twitter:site` as `@Lovable`.
- `public/robots.txt` and `public/sitemap.xml` use the
  `aero-flight-trivia.lovable.app` hostname.

These do not make the application execute differently, but leaving them behind
would make the repository misleading and retain project identifiers.

## Recommended migration sequence

### 1. Preserve a rollback point

Do this while GitHub sync and the Lovable deployment still work.

```sh
git status
git pull --ff-only
git switch -c chore/remove-lovable
git push -u origin chore/remove-lovable
```

Confirm that the latest desired Lovable changes are present in GitHub. Record
the current production URL and manually exercise the main menu, campaign,
settings, validator, Extreme briefing, and at least one minigame. Do not
disconnect GitHub or delete/unpublish the Lovable project yet.

Avoid rebasing, force-pushing, or rewriting the published `main` history while
the Lovable sync is still connected.

### 2. Standardize the local toolchain

Use one package manager. npm is recommended here because the existing README
already teaches npm and Node is required by the intended `node_server` output.

```sh
nvm install 24
nvm use 24
npm install
```

As part of the migration:

1. Add an `.nvmrc` containing `24`.
2. Add `"engines": { "node": ">=22.12.0" }` to `package.json`.
3. Change the package name from `tanstack_start_ts` to
   `aero-flight-trivia`.
4. Commit the generated `package-lock.json`.
5. Once npm is established in CI and local setup, remove `bun.lock` and
   `bunfig.toml`. Do not keep two competing lockfiles.

If the team chooses Bun instead, keep `bun.lock`/`bunfig.toml`, install Bun, and
replace every npm command in this guide with the Bun equivalent. Do not generate
or commit `package-lock.json` in that case.

### 3. Vendor all Lovable-hosted media

Run the following while the current Lovable app is still published. It reads
the manifests, downloads each original file into `src/assets`, and verifies the
recorded byte count.

```sh
node --input-type=module <<'NODE'
import { readdir, readFile, writeFile } from "node:fs/promises";
import { join } from "node:path";

const directory = "src/assets";
const origin = new URL("https://aero-flight-trivia.lovable.app/");
const manifests = (await readdir(directory))
  .filter((name) => name.endsWith(".asset.json"))
  .sort();

if (manifests.length !== 31) {
  throw new Error(`Expected 31 manifests from this audit; found ${manifests.length}`);
}

let total = 0;
for (const manifest of manifests) {
  const metadata = JSON.parse(await readFile(join(directory, manifest), "utf8"));
  const response = await fetch(new URL(metadata.url, origin), {
    headers: { referer: origin.href },
  });
  if (!response.ok) {
    throw new Error(`${manifest}: HTTP ${response.status}`);
  }

  const bytes = Buffer.from(await response.arrayBuffer());
  if (bytes.length !== metadata.size) {
    throw new Error(
      `${manifest}: expected ${metadata.size} bytes, downloaded ${bytes.length}`,
    );
  }

  await writeFile(join(directory, metadata.original_filename), bytes);
  total += bytes.length;
  console.log(`${metadata.original_filename}: ${bytes.length} bytes`);
}

console.log(`Downloaded ${manifests.length} files (${total} bytes)`);
NODE
```

Then convert the four consuming components to normal Vite asset imports. For
example:

```ts
import moonPortraitUrl from "@/assets/seus-moon.png";

// ...
<img src={moonPortraitUrl} alt="" />;
```

Replace every `something.url` reference with the imported URL string. After all
31 files are imported normally:

1. Delete all `src/assets/*.asset.json` manifests.
2. Run a production build.
3. Inspect the built `.output/public/assets` directory and confirm that the
   media files are present.
4. Exercise the title background, celebration/overload art, every Extreme
   briefing slide, and its video.
5. Confirm this search has no result outside this guide:

```sh
git grep -niE '(__l5e|asset_id|r2_key|project_id)' -- ':!cursor-migration.md'
```

The current media set is small enough for regular GitHub storage: about
26.1 MiB total, with no individual file near GitHub's 100 MB limit. Git LFS is
not required for the current files.

### 4. Replace the Lovable Vite wrapper

Replace `vite.config.ts` with this framework-native configuration. This exact
shape was build-tested during the audit.

```ts
import tailwindcss from "@tailwindcss/vite";
import { tanstackStart } from "@tanstack/react-start/plugin/vite";
import react from "@vitejs/plugin-react";
import { nitro } from "nitro/vite";
import { defineConfig } from "vite";
import tsConfigPaths from "vite-tsconfig-paths";

export default defineConfig({
  plugins: [
    tailwindcss(),
    tsConfigPaths({ projects: ["./tsconfig.json"] }),
    tanstackStart({
      server: { entry: "server" },
      importProtection: {
        behavior: "error",
        client: {
          files: ["**/server/**"],
          specifiers: ["server-only"],
        },
      },
    }),
    nitro({ preset: "node_server" }),
    react(),
  ],
  css: { transformer: "lightningcss" },
  server: {
    host: "127.0.0.1",
    port: 8080,
  },
});
```

`node_server` is a portable default for local verification and ordinary Node
hosting. If the replacement host is Cloudflare, Vercel, Netlify, Bun, or
another platform, deliberately select and test that platform's Nitro preset
instead.

Update the scripts in `package.json`:

```json
{
  "scripts": {
    "dev": "vite dev",
    "build": "vite build",
    "build:dev": "vite build --mode development",
    "start": "node .output/server/index.mjs",
    "preview": "node .output/server/index.mjs",
    "typecheck": "tsc --noEmit",
    "lint": "eslint .",
    "format": "prettier --write ."
  }
}
```

Now remove the wrapper and regenerate the chosen lockfile:

```sh
npm uninstall --save-dev @lovable.dev/vite-tanstack-config
npm install
```

Keep `@tanstack/react-start`, `@tanstack/react-router`, `@vitejs/plugin-react`,
`@tailwindcss/vite`, `vite-tsconfig-paths`, `vite`, and `nitro`; they are
framework dependencies, not Lovable dependencies. Keep `src/start.ts` and
`src/server.ts`.

Vite 8 can replace `vite-tsconfig-paths` with
`resolve: { tsconfigPaths: true }`. That is an optional follow-up cleanup, not
necessary for the initial migration.

### 5. Remove Lovable telemetry code

In `src/routes/__root.tsx`:

1. Remove the `reportLovableError` import.
2. Remove the effect that calls it from `ErrorComponent`.
3. If that was the only effect in the file, remove `useEffect` from the React
   import.

Then delete `src/lib/lovable-error-reporting.ts`.

Keep the generic `console.error`, `src/lib/error-capture.ts`, and
`src/lib/error-page.ts`; those are application-owned error handling. A
provider-neutral monitoring SDK such as Sentry can be added later, but it is
not required to run locally.

### 6. Remove Lovable metadata and replace production URLs

1. Rewrite `README.md` with the npm setup and build/start commands from this
   guide. Remove the Lovable editor and Lovable live-app sections.
2. Remove the Lovable block from `AGENTS.md`. Delete the file if it becomes
   empty, or replace it with project-owned contributor instructions.
3. Review `.lovable/plan/**`, `.lovable/plan.md`, and
   `.lovable/north-star.md`. Move any useful product notes to `docs/`, then
   delete `.lovable/`.
4. Remove `twitter:site: @Lovable` from `src/routes/__root.tsx`, or replace it
   with the project's actual account.
5. Replace the Lovable hostname in `public/robots.txt` and
   `public/sitemap.xml` with the new canonical production URL.
6. If npm was selected, remove `bunfig.toml`; its Lovable package exceptions
   should not be copied elsewhere.

Finally run:

```sh
git grep -niE '(lovable|__l5e|@lovable\.dev|lovable\.app|asset_id|r2_key)' \
  -- ':!cursor-migration.md'
```

The target is no matches. References in Git history are harmless and do not
need to be rewritten.

### 7. Establish a clean verification workflow

First verify the migration without mixing in mass formatting:

```sh
npm ci
npm run typecheck
npm run build
PORT=3000 HOST=127.0.0.1 npm start
```

Open `http://127.0.0.1:3000` and complete the acceptance checklist below.

Handle the existing formatting debt in a separate commit:

```sh
npm run format
npm run lint
```

Review that formatting-only diff before committing it. Also consider adding a
`check` script and CI job that run typecheck, lint, and build on every pull
request. There is currently no automated test suite, so browser smoke testing
is important.

### 8. Deploy and cut over

For a generic Node host, use:

```sh
npm ci
npm run build
HOST=0.0.0.0 PORT=3000 npm start
```

Deploy the complete `.output` directory or let the platform run the build.
Configure the new custom domain, HTTPS, and any health check. Update the
sitemap, robots file, and social metadata before moving search traffic.

Keep the old Lovable deployment available until the new deployment serves all
31 media files and passes the acceptance checklist.

### 9. Stop Lovable's GitHub synchronization

After the replacement branch is merged, pushed, deployed, and backed up:

1. Open the project in Lovable.
2. Go to **Project settings → Git → GitHub**.
3. Open the active repository connection's menu and choose **Disconnect**.
4. Complete Lovable's confirmation prompt.
5. Refresh the settings and confirm that the project no longer shows a
   connected repository.
6. Push a harmless documentation commit from local development and verify that
   no Lovable-generated commit or project update appears.

According to Lovable's current documentation, disconnecting stops two-way sync
but leaves both the GitHub repository and the Lovable project intact. If
reconnected later, Lovable creates a new repository rather than reconnecting
the old one.

Only if no other Lovable project needs the shared GitHub authorization, remove
the workspace-level connection under **Workspace settings → Git → GitHub** and
review/revoke the Lovable GitHub App installation in GitHub's application
settings. Do not revoke a workspace-wide installation if other projects still
use it.

Once the replacement deployment has been stable for an agreed rollback window,
unpublish, archive, or delete the old Lovable project as desired. This last step
is optional for code independence and should be treated as destructive.

## Acceptance checklist

- A clean clone works with Node 24 and `npm ci`.
- `npm run dev` serves the app at `http://127.0.0.1:8080`.
- `npm run typecheck` passes.
- `npm run build` creates `.output`.
- `npm start` serves `/` with HTTP 200 after a build.
- Browser developer tools show no requests to `/__l5e/` or any Lovable domain.
- All 31 local images/video load, including the full Extreme briefing.
- Main campaign progress survives a reload through `localStorage`.
- Campaign, Practice, High-Speed, Review, Mastery, and Extreme modes open.
- Electric Recall, Light Cycle, Neon Maze, and Memory Gauntlet accept keyboard
  input.
- Audio starts only after user interaction and mute/volume settings work.
- The in-app validator reports the expected 333-question curriculum.
- The not-found page and forced error boundary render correctly.
- `robots.txt`, `sitemap.xml`, canonical URLs, and social metadata use the new
  production identity.
- The repository and lockfile contain no Lovable package.
- The source search in step 6 returns no matches outside this guide.
- Lovable's project settings show no GitHub repository connection.
- A normal push to GitHub does not reappear in Lovable.

## Optional simplification after migration

The application has only one route and no server data or server functions, so
it could later be converted from TanStack Start SSR to a plain Vite client-side
React app. That would remove Nitro and the production Node server. It is not
necessary for Lovable independence, and combining that architectural change
with the dependency migration would make rollback and debugging harder. Finish
the like-for-like migration first.
